# ADR-0013: WhatsApp Finance Entry Adapter — Architecture and Execution Identity

- Status: Accepted
- Date: 2026-08-10
- Authors: Claude Code

---

# Context

Phase 3B makes the AI Finance Inbox pipeline (Slack front door → `02-finance-intent-router.json` → `10-handle-create-expense.json`) reachable through WhatsApp. `docs/workflows/finance-inbox-contract.md`'s "Adding a New Channel" section describes the expected shape for any new front door: receive the channel's native event, normalize it into the Finance Inbox Request Contract, generate `workflowExecutionId` exactly once as the front door's own `$execution.id`, call the Router via `Execute Workflow`, relay `response.message` back through the channel.

That recipe implicitly assumes one workflow plays the "front door" role end-to-end — true for `01-finance-inbox-entry.json` (Slack), whose own `Slack Trigger - Inbox Message` node IS the top-level, webhook-triggered execution. WhatsApp does not have that shape in this repository. `workflows/integrations/01-whatsapp-gateway-webhook.json` already owns the real inbound webhook (`https://automation.eyan.fyi/webhook/whatsapp/webhook`), Meta's verification handshake, and Meta payload parsing/normalization — and its own architecture doc (`docs/workflows/whatsapp-gateway-architecture.md`) explicitly documents its terminal `Ready For AI / CRM Processing` NoOp node as "future milestone plugs in here." Building a second, independent WhatsApp-triggered workflow would either duplicate all of that (webhook verification, Meta's `whatsapp_business_account` envelope parsing, message/status-callback disambiguation) or require Meta to be configured with two webhook URLs for one number, which the Cloud API does not support.

This creates two decisions this ADR needs to settle explicitly, not silently: (1) where the new Finance-specific workflow lives and how it's invoked, and (2) — critical, and easy to get silently wrong per `docs/workflows/finance-inbox-contract.md`'s own warning — which workflow is allowed to generate `workflowExecutionId`.

# Decision

**1. The new workflow (`workflows/finance/03-whatsapp-finance-entry.json`, `FinanceWhatsAppEntryWf01`) is `Execute Workflow`-triggered, not webhook-triggered, and is invoked from the Gateway's existing `Ready For AI / CRM Processing` extension point.** `workflows/integrations/01-whatsapp-gateway-webhook.json` gained one additive node pair (`Call WhatsApp Finance Entry` → `Finance Entry Dispatched`) wired from that exact NoOp — no existing node, connection, or branch in the Gateway was altered. The Gateway keeps sole ownership of everything WhatsApp-transport-specific (webhook, Meta verification, payload parsing); the new adapter owns only the Finance-specific translation (WhatsApp envelope → Finance Inbox Request Contract → Router → reply).

**2. The adapter does NOT generate `workflowExecutionId` via its own `$execution.id`. It forwards, unchanged, the value the Gateway already generated.** The Gateway's `Normalize WhatsApp Messages` node already sets `workflowExecutionId: $execution.id` — using the Gateway's own execution, since the Gateway is the actual top-level, webhook-triggered execution for this chain (the adapter's execution is a *child* of it, created by the `Execute Workflow` call). The adapter's `Validate WhatsApp Event Input` node requires this field non-empty; `Build Finance Inbox Request` copies it through verbatim. This makes the WhatsApp chain's `workflowExecutionId` semantics identical to Slack's in effect (generated exactly once, at the true channel-entry boundary, threaded unchanged through every subsequent hop) even though, unlike Slack, that boundary is split across two workflow files.

`workflowName`, by contrast, is **not** forwarded — the adapter sets its own (`"03-whatsapp-finance-entry"`), not the Gateway's (`"whatsapp-gateway-webhook"`), matching the established per-hop-self-identifies convention already used by `workflows/crm/03-ai-qualification.json`'s `Call AI Core` node and `10-handle-create-expense.json`'s own Finance API call (see that workflow's Idempotency section). Only `workflowExecutionId` is the one constant thread across every hop; `workflowName` identifies which workflow is making *this* particular call, for audit/log purposes.

# Alternatives Considered and Rejected

- **A second, independent WhatsApp webhook-triggered workflow, duplicating the Gateway's verification/parsing.** Rejected: Meta's Cloud API delivers all inbound events for a phone number to exactly one configured webhook URL — a second webhook node would either never receive traffic or require reconfiguring Meta to point away from the existing Gateway, silently breaking the Gateway's own `"eyan-test"` keyword-reply capability and any future non-Finance consumer of the same events. It would also re-implement Meta's `whatsapp_business_account` envelope parsing and message/status-callback disambiguation a second time, for no benefit.
- **Generate a fresh `workflowExecutionId` inside the adapter, via its own `$execution.id`.** Rejected: this is exactly the failure mode `docs/workflows/finance-inbox-contract.md`'s "Generating `workflowExecutionId`" section warns is easy to introduce silently and only breaks under retry — a redelivered Meta webhook would still get a fresh Gateway execution (and thus a fresh ID from the Gateway) on each redelivery regardless, so nothing is gained by regenerating it again a hop later, while doing so would make the adapter itself capable of *breaking* an otherwise-consistent ID it was simply supposed to relay.
- **Have the Gateway build the Finance Inbox Request Contract directly, with no separate adapter workflow.** Rejected: this would make `01-whatsapp-gateway-webhook.json` a Finance-domain-aware workflow, contradicting its own architecture doc's stated boundary ("this is a channel gateway, not a business-domain workflow; CRM/Finance/future domains are expected to call it themselves") and `docs/workflows/finance-inbox-contract.md` Decision 4's "only the front-door tier knows which channel it is" split (the Router tier already assumes a single, contract-conforming caller — a general-purpose gateway is a worse fit for that role than a domain-owned adapter).
- **Route the Gateway's outbound response through the Gateway itself, with the adapter only building the Finance request (not calling Outbound Send).** Rejected as an unnecessary extra hop back through the Gateway: `docs/workflows/whatsapp-gateway-architecture.md` already documents `02-whatsapp-outbound-send.json` as "`Execute Workflow`-callable, not bound to any one caller" — precisely so that a domain workflow like this adapter can call it directly, the same way the Gateway's own `"eyan-test"` path already does.

# Consequences

- `workflowExecutionId` generation is now split across two workflow files for the WhatsApp channel specifically (Gateway generates, Adapter forwards) — a structural asymmetry with Slack (where `01-finance-inbox-entry.json` does both in one file). This is inherent to WhatsApp already having a shared, non-Finance-specific Gateway that Slack has no equivalent of; a future channel with its own dedicated, single-purpose front door (e.g. a hypothetical Finance-only Telegram bot) would not need this split.
- The Gateway (`workflows/integrations/01-whatsapp-gateway-webhook.json`) is no longer purely a passthrough with one dead-end NoOp for non-test messages — it now has a live downstream consumer. Its own documentation (`docs/workflows/whatsapp-gateway-architecture.md`, `docs/workflows/01-whatsapp-gateway-webhook.md`) is updated in this same phase to reflect that, since the diagram's own "future milestone plugs in here" note is no longer accurate.
- Any future non-Finance consumer of the Gateway's normalized WhatsApp events (a CRM or support-domain workflow) can be added the same way — one more branch off `Normalize WhatsApp Messages`'s output, calling its own domain-specific adapter — without touching this Finance adapter or the Router.
- WhatsApp media messages (images, documents) are not extracted as Finance Inbox `attachments` this phase — the Gateway itself does not resolve WhatsApp media IDs to downloadable URLs (a separate, authenticated Graph API call it does not currently make; see `docs/workflows/01-whatsapp-gateway-webhook.md`). A non-text WhatsApp message reaches the adapter with an empty `rawText` and `attachments: []`, which the Router/Handler already handle safely (routes to `UNRECOGNIZED`/`clarify`, never a crash) — this is a known, documented limitation, not a silent gap.
